# Task Start (task.\*.md 駆動の単発タスク遂行)

## 概要

ユーザーが指定した `task.*.md`、または **実行ディレクトリ (cwd) 直下に新規作成する** `task.*.md` を **そのタスクの依拠文書（メモ・進捗・成果物リンクの集約先）** として扱い、1 タスクを完遂するための skill。名前は内容が分かる意味のあるものを Claude が命名する（詳細は後述「命名規約」）。最終的に「原因 / 修正 / 検証 / 意思決定」をメモとして残す（詳細は §4「メモセクションの育て方」）。

**ファイルの場所**:

- reviewd は **単一 Go リポジトリ**（`cmd/` `internal/` `doc/` のみ）なので、通常は **リポジトリ直下 = cwd 直下** に置くことになる。
- **既存ファイル**: ユーザーが引数 / 会話文脈で示したパスをそのまま使う（絶対パスでも相対パスでも可）。場所を勝手に動かさない。
- **新規作成**: `pwd` で確認した **実行ディレクトリの直下** に作る。ユーザーが特に指定しない限り、上位ディレクトリ・別サブツリーへ作らない。

**命名規約**:

- `task.*.md` は `.gitignore` に登録済みで、すべて commit 対象外になる運用。**Claude が自動で作成するタスクファイルは必ず `task.*.md` パターンに従う**。
- **`task.auto.md` のような汎用名は使わず、必ず内容が分かる意味のある名前を付ける**。名前は **Claude が自律的に決めてよい**（ユーザーに確認しない）。優先順位:
  - issue/PR 駆動: `task.<番号>.md`（例 `task.42.md`）
  - トピック駆動: `task.<kebab-slug>.md`（例 `task.ghostty-sink.md` / `task.gc-command.md`）
  - OpenSpec change 起点: `task.<change名>.md`
- それ以外のファイル名（例: `TASK.md`, `notes.md`, `todo-42.md`）は **使わない**。gitignore から漏れて誤って commit される事故 / 内容不明を防ぐため。

> 例外: リポジトリ直下の既存 `task.auto.md` は reviewd の初期開発（MVP 全体）で使われた歴史的なファイル。**続行モードではそのまま使ってよい**が、新規作成では汎用名を使わない。

**コアな考え方**:

- `task.*.md` は「**作業ログ**」と「**チェックリスト**」と「**最終的なナレッジ**」を 1 ファイルに集約するための器。
- セッションが落ちても、別エージェントに引き継いでも、このファイルを読めば「何をしようとしていて、どこまで進み、なぜそうしたか」が分かる状態を維持する。
- 完了後のクリーンアップ（削除 / PR description への転記）は **ユーザーが手で行う**。skill 側では消さない。

**引数**: $ARGUMENTS — 次のいずれかを受け取る前提:

| 引数のタイプ            | 判定方法                                                              | 対応モード                                                                                        |
| ----------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **タスクファイルパス**  | `task.*.md` パターンに合致 / 既存ファイルとして読める                 | **続行モード**（§1）                                                                              |
| **GitHub issue/PR URL** | `github.com/<owner>/<repo>/(issues\|pull)/<num>` または `#<num>` 形式 | **新規作成モード**。`gh issue view` / `gh pr view` でタイトル・本文・ラベルを取得して雛形に流し込む |
| **OpenSpec change 名**  | `openspec/changes/<name>/` パス、または `openspec list` に出る名前    | **新規作成モード**。proposal / tasks を読んで背景・受け入れ条件を把握（後述 §OpenSpec 連携）      |
| **自由記述 / なし**     | 上記いずれにも当てはまらない                                          | **新規作成モード**。AskUserQuestion でタイトル・チェックリスト粒度をユーザーに確認しつつ作る      |

判定は引数文字列の先頭を見るだけで十分。複数渡された場合（例: タスクファイルパス + issue URL）は **ファイルを依拠文書として扱い、URL は冒頭の参照リンクに追記** する。

> Notion MCP は reviewd では未設定。Notion URL を渡されたら、内容をユーザーに貼ってもらうか、URL だけを `## 関連リンク` に記録して進める。

## reviewd: OpenSpec ライフサイクルとの連携

このリポジトリは **OpenSpec** を起点とした開発ライフサイクルを採用している。運用ルールは [doc/development/openspec.md](../../doc/development/openspec.md) で定義する。

```text
Issue → OpenSpec(proposal / tasks) → task-start → 実装 → Archive → Review → doc更新
```

**役割分担（混ぜない）**:

- **OpenSpec `tasks.md`**: その Change の受け入れ条件。共有される変更の契約。**commit 対象**。
- **task-start `task.*.md`**: 個人の作業ログ・試行錯誤・現在地メモ。**gitignore 対象で commit されない**。

**OpenSpec change を起点に task-start を使う**:

1. `openspec show <change>` / `openspec/changes/<change>/proposal.md` `tasks.md` を読んで背景・受け入れ条件を把握する
2. cwd 直下に `task.<change>.md` を新規作成し、冒頭 `## 関連リンク` に `openspec/changes/<change>/` へのパスを記載する
3. `tasks.md` の項目を **そのままコピーせず**、実装手順に落とした個人チェックリストとして雛形に展開する（tasks.md = 契約 / task.\*.md = 作業ログ）

進行中 change の一覧は `openspec list` で確認できる。

**原則すべての変更で OpenSpec change を作成**する運用（例外的に小規模な変更のみスキップ可）。change がまだ無い規模の変更に着手しようとしている場合は、先に `openspec new change <name>` で change を作るようユーザーに促してよい。小規模でスキップする場合は task-start だけで進めてよい。

**reviewd でスキップしてよい / してはいけない目安**:

- スキップ可: typo、ログ文言、テスト追加、既存関数のリファクタ
- スキップ不可: **新しいイベント種別の追加**（review submitted / CI 完了 等）、**外部プロセスの起動方式の変更**（headless claude / Ghostty / tmux）、**config.yaml・rules.yaml のスキーマ変更**、**launchd まわりの変更**。いずれも「外部との契約」か「意思決定を伴う設計変更」に当たる。

## 現在の状態

- 実行ディレクトリ (cwd): !`pwd`
- ブランチ: !`git branch --show-current 2>/dev/null || echo "(git 管理外)"`
- 直近 commit: !`git log -1 --oneline 2>/dev/null || echo "(commit なし)"`
- cwd 直下の task.\*.md: !`ls -1 task.*.md 2>/dev/null || echo "なし"`
- task.\*.md は gitignore か: !`git check-ignore -v task.auto.md 2>/dev/null || echo "(ignore 設定を要確認)"`
- 進行中の OpenSpec change: !`openspec list 2>/dev/null || echo "(openspec CLI 未導入 / change なし)"`
- 紐づく PR: !`gh pr view --json number,title --jq '"#\(.number) \(.title)"' 2>/dev/null || echo "PR 未作成"`

> **`!` コマンドは必ず `|| echo` でフォールバックさせる**。reviewd は commit ゼロの状態から開発が始まった経緯があり、`git log -1` が非 0 で終了して skill の読み込み自体が失敗した実績がある（`2>/dev/null` だけでは終了コードは 0 にならない）。

## ワークフロー

### 0. モード判定

冒頭で次のいずれかに振り分ける。**判定にあたっては引数のパス指定 > cwd 直下の存在 > リポジトリ内の他の場所** の優先順位で対象を決める。

| 状況                                                | モード               | 最初にやること                                                                      |
| --------------------------------------------------- | -------------------- | ----------------------------------------------------------------------------------- |
| 引数で具体的なパス（`task.foo.md`）が渡された       | **続行（指定優先）** | そのパスを Read。存在しなければユーザーに確認                                       |
| 引数が GitHub issue/PR URL                          | **新規作成**         | `gh issue view` / `gh pr view` で内容取得 → 雛形へ流し込み → AskUserQuestion        |
| 引数が OpenSpec change 名 / パス                    | **新規作成**         | `openspec show <change>` で proposal / tasks 取得 → 雛形へ展開 → AskUserQuestion    |
| 引数なし、cwd 直下に `task.*.md` が 1 つ            | **続行**             | ファイル全文を Read。未完了 `[ ]` を抽出                                            |
| 引数なし、cwd 直下に `task.*.md` が複数             | **要確認**           | 一覧を提示し AskUserQuestion で選んでもらう                                         |
| 引数なし、cwd 直下には無いがサブツリー / 上位に存在 | **要確認**           | 検出されたパスを提示し「これを使うか / cwd 直下に新規作成するか」を AskUserQuestion |
| 引数が自由記述だけ                                  | **新規作成**         | 概要をタイトルに使う。詳細は AskUserQuestion で補う                                 |
| 何もない                                            | **要確認**           | AskUserQuestion で issue URL / change 名 / タスク概要を聞き、新規作成モードへ       |

**禁止事項**: §注意事項の「ファイル操作の禁止事項」を必ず守る（上書き禁止 / 命名規約 / cwd 直下のみ / commit しない / 冒頭 2 行を消さない）。また、**タスク着手時にブランチを切らない / 切り替えない**。現在のブランチのまま作業を始める（詳細は §注意事項）。

### 1. 続行モード: 既存ファイルの読解

対象の `task.*.md` を Read で全文読み、以下を抽出する:

- **タイトル**: 最初の `# ...` 行（多くの場合 issue タイトル）
- **`## 関連リンク`**: 既に作成・参照済みの issue / PR / OpenSpec change / 設計 doc リンク（無ければタイトル直下に新設する。以降この節を成果物 URL の集約先とする）
- **チェックリスト**: `- [ ]` / `- [x]` の項目
- **`## メモ` セクション**: 既存の原因分析・修正方針・検証メモ
- **冒頭の指示文**: 「メモはこのファイルに」「重要ドキュメントは適宜残して」等のメタ指示

未完了 `[ ]` 項目を `TodoWrite` に 1 タスク 1 項目で投入する（タイトルはチェックリスト原文）。既に `[x]` の項目は登録しない。

**現在地の把握 (再開時に必須)**: チェックリストだけ見て即実装に入らない。`## メモ` を読んで次を整理してから着手する:

- 最後に書かれた仮説 / 試行は何か（`### 原因` / `### 修正` の末尾）
- 既に却下した案 / 試して外したアプローチはあるか（`### 意思決定の理由`）
- 「### 残課題」「### TODO」「### 行き詰まり」等の動的な見出しに残された未消化メモ
- 直近の `[x]` チェック項目と `### 修正` の整合（書き忘れ・齟齬があれば追記）

**reviewd 特有の再開時チェック**: チェックリストが全部 `[x]` でも「動く状態」とは限らない。次の 3 つは task ファイルに書かれていても実態がズレていることがあるので、`## メモ` の記述を鵜呑みにせず実際に確認する。

- `go build ./...` / `make test` が通るか（コード側）
- `~/.reviewd/` が存在するか（実機検証の成果物は掃除されて消えていることがある）
- `launchctl list | grep reviewd` で常駐しているか（実装済み ≠ 登録済み）

これらを 1-2 行でユーザーに「現在地サマリ」として返してから次サブタスクへ進むと、認識ズレが起きにくい。

### 2. 新規作成モード: 雛形の作成

#### 2-a. 配置場所とファイル名の決定

**配置場所**: 原則として **実行ディレクトリ (cwd) の直下**。`pwd` で確認した場所にそのまま作る。ユーザーが明示的に指示した時だけ他の場所に置く。

既存ファイルが別の場所にあって続行モードになる場合は、§1 の対象パスをそのまま使い、cwd 直下に複製しない。

**ファイル名**: **必ず `task.*.md` パターン**、かつ **内容が分かる意味のある名前**を使う。名前は **Claude が自律的に決める**（ユーザーへの確認は不要）。優先順位:

1. issue/PR 駆動: `task.<番号>.md`
2. トピック駆動: `task.<kebab-slug>.md`
3. OpenSpec change 起点: `task.<change名>.md`

既に同名ファイルがある場合は別名にする（上書き禁止）。

> `task.*.md` は `.gitignore` で除外されるため、PR に混入する心配はない。逆に **このパターンから外れた名前を作ると commit に紛れ込むリスク** があるため厳守。

#### 2-b. 引数ソースからの情報取り込み

雛形を書き始める前に、引数の種類に応じて **タイトル / 本文 / ラベル / 関連リンク** を取得しておく。

| 引数種別                          | 取得コマンド / ツール                                                 | 取り込む項目                                               |
| --------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------- |
| GitHub issue                      | `gh issue view <num> --json title,body,labels,assignees,url,comments` | タイトル、本文要約、ラベル、最新コメントのうち仕様確定情報 |
| GitHub PR                         | `gh pr view <num> --json title,body,url,headRefName,baseRefName`      | タイトル、PR description、対象ブランチ                     |
| `owner/repo#N` 形式や別リポジトリ | `gh issue view <num> --repo <owner>/<repo> ...`                       | 同上                                                       |
| OpenSpec change                   | `openspec show <change>` / `proposal.md` `tasks.md` を Read           | Why / What Changes、受け入れ条件、design.md の設計判断     |
| 自由記述                          | （取得無し）                                                          | ユーザー発話そのまま                                       |

**重要**:

- Issue/PR の本文をそのままコピペせず、**チェックリスト化できる単位に要約** する。長文は `### 仕様` / `### 参考` 見出しに別途貼る。
- OpenSpec の `tasks.md` は受け入れ条件であって作業手順ではない。**実装順に並べ替え、調査・検証ステップを足して**チェックリスト化する。
- ネットワーク取得が失敗した場合は AskUserQuestion でフォールバック（手入力 / 後で再試行）。

#### 2-c. 雛形

取得済み情報を元に、次のテンプレートで作る:

```markdown
<ファイル名> を見てタスク進めて
タスクの実行におけるメモはこのファイルに行って、実装に進めるにあたって重要なドキュメントは適宜残してください。

# <タイトル>

## 関連リンク

<!-- タスク遂行中に作成 / 参照した issue・PR・サブタスク・OpenSpec change・設計 doc は必ずここ（ページ最上部）に集約する。新規作成したら即追記。 -->

- Issue: <引数で受け取った issue URL / なければ「なし」>
- PR: <未作成 / 作成したら即 URL を追記>
- OpenSpec change: <openspec/changes/<name>/ / なし>
- 関連 issue・サブタスク: <分割・派生で作ったものを追記 / なし>
- その他参照: <設計 doc など / なし>

## チェックリスト

- [ ] <最初に思いつくサブタスク>
- [ ] <次のサブタスク>
- [ ] <テスト追加 / make pre-commit 通過>

---

## メモ

### 原因

### 修正

### 検証

### 意思決定の理由

### 残課題
```

雛形の **チェックリストはあくまで仮**。実コードを軽く偵察（Read / Grep）してから「この粒度で進めて良いか」を AskUserQuestion で確認する。

- 不明な部分は `<TBD>` のままにしておく
- 仮のチェックリスト項目に確信が無いことを明記してから尋ねる

ユーザー承認後に Write で保存し、続行モードと同じ手順で `TodoWrite` に投入する。

> 雛形だけでは「メモをどこまで具体的に書くか」が伝わりにくい。**埋まった状態の完全な実例は同ディレクトリの [`examples.md`](examples.md) を参照**。新規作成直後 / 進行中 / 完了直前の 3 段階で、どの見出しがどこまで埋まっているのが正常か、また大きめのタスクで見出しをどう増やすかが分かる。

### 3. サブタスクの逐次実行

**成果物 URL の記録（必須・最優先）**: タスク遂行中に **PR / issue / サブタスク issue / OpenSpec change を新規作成したら、作成したコマンドが成功した瞬間に、その URL とパスを冒頭の `## 関連リンク` に追記する**。`gh pr create` / `gh issue create` の標準出力に出る URL をそのまま貼る。これを後回しにしない（セッションが落ちると「何を作ったか」が永久に失われるため）。`## 関連リンク` が無い既存ファイルなら、タイトル直下に新設してから追記する。

`TodoWrite` の項目を 1 つずつ `in_progress` にして実行する。**1 サブタスクが完了したら即座に**:

1. **実装系サブタスクなら `make pre-commit`**（= `fmt` + `vet` + `test`）を回す。範囲を絞りたいときは `go test ./internal/<pkg>/...`
2. `TodoWrite` を `completed` に
3. 対象 `task.*.md` のチェックリスト該当行を `[ ]` → `[x]` に Edit
4. 必要なら `## メモ` に下記 4 項目のうち判明した部分を追記（後述 §4）

`make pre-commit` が失敗したらサブタスクは **未完了のまま**。`### 残課題` に「vet で X が出ている」を 1 行残してから次に進むか修正する。

> `make fmt` は `gofmt -l -w .` なので **ファイルを書き換える**。実行後に差分が増えるのは正常。`make lint`（golangci-lint）は未インストールならスキップされるので、通ったことの証明にはならない。

**重要**: チェックリストの更新を「全部終わってから一気に」ではなく **1 項目ごとに即時** に行う。理由はセッション中断時の復旧性。

**Edit でチェック行を `[x]` 化する際の注意**:

- `- [ ]` だけだと `old_string` が unique にならず Edit が失敗する。必ず **アイテム名込み** で指定する（例: `- [ ] internal/store のテスト追加` → `- [x] internal/store のテスト追加`）
- それでも複数該当する場合は前後 1-2 行をコンテキストに含めて unique にする
- `replace_all` は使わない（他のチェックボックスも巻き込むため）

新たに判明したサブタスクがあれば:

- 既存チェックリストに `- [ ]` で追記（位置は実行順序に沿った場所）
- 同時に `TodoWrite` にも追加
- 1 項目だけの軽い branch out なら、サブ箇条書き `  - [ ]` でネストしても良い

### 4. メモセクションの育て方

`## メモ` 配下に **最低限**次の 4 見出しを置き、判明し次第埋めていく:

| 見出し               | 書く内容                                                                                 | reviewd での例                                                                                                        |
| -------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `### 原因`           | なぜその不具合 / 課題が発生していたかの **root cause**。表面的な症状ではなく構造的な理由 | 「`.gitignore` の `reviewd` が先頭 `/` 無しのため、パターンが全階層に効いて `cmd/reviewd/` ごと除外されていた」        |
| `### 修正`           | どのファイルをどう変えたか。**ファイル名と変更要点** を必ず書く                          | 「`.gitignore:5` — `reviewd` → `/reviewd`（ルート直下のバイナリのみに限定）」                                          |
| `### 検証`           | テスト・手動確認など、**どう壊れていないか** を再確認した手段                            | 「`git check-ignore -v cmd/reviewd/main.go` が修正前はヒット、修正後は非ヒットになることを確認」                       |
| `### 意思決定の理由` | 採用案の根拠、却下した代替案、スコープ判定                                               | 「`!cmd/reviewd/` の negate 追加案は、ignore パターンが増えるほど読み解けなくなるため却下。先頭 `/` でアンカーする方を採用」 |

**書き方の原則**:

- **未来の自分 / 別エージェントへの引き継ぎ書** だと思って書く。「これを読めば PR description が書ける」を目標に。
- ファイル参照は `internal/runner/runner.go:143` 形式で行番号付き。
- 引用するなら ` ```go ``` ` のコードフェンス。
- **外部コマンドの実測結果は必ず貼る**。reviewd は `gh` / `git` / `claude` / `osascript` の出力形状に依存しているため、「実際にこう返ってきた」が最重要の根拠になる（例: `claude -p --output-format stream-json` の最終行の JSON 形状）。憶測で書かない。
- **不要になったメモは削除してコンテキストを軽く保つ**（ユーザー明示の好み 2026-06-01「不要になった対応項目、間違っていたものはタスクファイルの中から消して　余計なコンテキストをなくしたいので」）。誤りと確定した分析・スコープ外になった対応項目は消してよい。ただし**採用 / 却下の意思決定理由（### 意思決定の理由）は残す**（「なぜその方向にしたか」は将来も価値があるため）。進行中で結論が出ていない試行錯誤は「修正前: ... / 修正後: ...」の並置で残す。
- TODO が残ったら「### 残課題 / TODO」見出しを追加して `- [ ]` で書き残し、チェックリスト本体にも転記する。

### 5. 「実装に進めるにあたって重要なドキュメント」の残し方

冒頭指示文 (`実装に進めるにあたって重要なドキュメントは適宜残してください`) を **コードを書く前 / 書きながら** 実践する:

- 関連する既存実装の参考箇所 → `### 参考` 見出しに `internal/app/app.go:327` + 1 行コメント
- 仕様の根拠 → `### 仕様` 見出しに `doc/design.md` の節リンク、または OpenSpec change へのパス
- **外部ツールの実測**（`gh` の JSON 形状 / `claude` の stream-json 形状 / AppleScript 辞書の command 名など）→ `### 実測` 見出しにコマンドと出力を貼る
- ロールバック手順や手動確認手順（`~/.reviewd/` を退避する、`launchctl bootout` する等）

書きすぎは害ではない。**実コードに残しても邪魔な「なぜ」は task.\*.md 側に逃がす** くらいの感覚で OK（どうせ gitignore で commit されない）。

### 6. 着地確認 (タスク完了直前)

すべての `- [ ]` が `- [x]` になったら、ユーザーに渡す前に以下を確認:

- [ ] チェックリストに未消化項目が残っていないか（`grep -n '\[ \]' <ファイル名>`）
- [ ] `## メモ` の 4 見出し（原因 / 修正 / 検証 / 意思決定の理由）が **すべて埋まっている** か。判らなかった項目は「不明」「該当なし」と明記
- [ ] **このタスク中に作成 / 参照した issue・PR・サブタスク・OpenSpec change が、すべて冒頭の `## 関連リンク` に記載されているか**（作成したのに貼り忘れていないか）
- [ ] `make pre-commit` を実行済みか
- [ ] 修正したファイルが `task.*.md` のメモから辿れる（ファイル名漏れがない）か
- [ ] **task ファイル内の仕様記述 と 実装（config のキー名 / rules.yaml のフィールド名 / CLI のフラグ名）のズレが無いか**。スキーマ変更を伴うタスクでは特に必須
- [ ] **OpenSpec change がある場合、`tasks.md` の受け入れ条件も満たしているか**。満たしていれば実装と同じ PR で `openspec archive <change>` するようユーザーに促す

**仕様記述と実装の整合チェック（スキーマ変更を伴うタスクでは追加実施）:**

config.yaml / rules.yaml のキー名、CLI のサブコマンド・フラグ名が変わったタスクでは、最後に必ず次を回す:

1. **旧キー名** を grep して残存箇所を検出する。reviewd は同じ名前が **4 箇所**に散るので取りこぼしやすい:
   - Go の struct tag（`internal/config/*.go`）
   - 雛形テンプレート（`internal/cli/templates/*.yaml`）
   - 設計ドキュメント（`doc/design.md`）
   - 導入手順（`README.md`）
2. **新キー名** も grep して、コメント・doc・README が新仕様で揃っているか確認する
3. ヒット箇所のうち「コメント / doc コメント」も同じ概念を語っていれば必ず一緒に更新

実装本体だけ書き換えて雛形テンプレートや README を旧仕様のまま残すと、**`reviewd init` が生成する config が壊れる**（`yaml.Strict()` で未知キーが弾かれるため即エラーになる）。コードレビューは差分しか見ないため気づかれない。

これらは **完了報告に先立つチェックリスト**。1 つでも欠ければ完了と言わない。

### 7. ユーザー向け最終報告

`task.*.md` の `### 原因 / 修正 / 検証 / 意思決定の理由` は**自分用の作業ログ**の見出しであり、人へ出す報告の書式ではない。

**そのまま PR description に貼れる体裁** でまとめる。`## Summary` / `## Test plan` のような PR 規約に近い構造にしておくと、ユーザーが後段で `gh pr create` するときに転記コストが最小化される。

```markdown
## Summary

<タイトル / 1-3 行で「何をなぜ変えたか」>

関連: <issue / OpenSpec change のパス>

## 原因

<root cause を 1-3 行。task.\*.md の `### 原因` から要約>

## 変更内容

- internal/runner/runner.go:143 — <要点>
- internal/config/config.go:56 — <要点>

## Test plan

- [x] <追加・更新したテストファイル名 + ケース>
- [x] <手動確認した手順（`reviewd poll --dry-run` 等）>
- [x] `make pre-commit` 通過

## 残課題

- なし
- or: <残課題>: 別 issue #N で追跡 / 後続 PR で対応 等

---

タスクファイル `<相対パス>` を最新化済み（gitignore 対象なので commit には含まれません）。

次のアクション:

1. 差分を確認 (`git diff`)
2. commit 作成
3. push / `gh pr create` で PR 作成（必要なら上記 Summary をそのまま description に貼り付け）
```

タスクファイルの削除・コミット・PR description への転記・push は **行わない**。ユーザーの操作を待つ。

## reviewd 固有の落とし穴

タスクを進める中で高確率で踏むもの。踏んだら `## メモ` に記録して、次のタスクで同じ穴に落ちないようにする。

**1. `.gitignore` のパターンは先頭 `/` でアンカーする**

`reviewd` と書くと gitignore パターンは全階層に効き、**`cmd/reviewd/` ディレクトリごと除外される**。`git status` に一切出ないため気づけない。ルート直下のビルド成果物だけを除外したいなら `/reviewd`。新しく ignore パターンを足すときは必ず `git check-ignore -v <実在するファイル>` で確認する。

**2. launchd の PATH には shim が入らない**

`gh` / `claude` は aqua / Homebrew の shim 配下にあり、launchd の既定 PATH では解決できない。`internal/daemon` は install 時に解決した PATH を plist へ焼き込む設計。**`gh` や `claude` を入れ替えたら `daemon install` をやり直す**必要がある。「ローカルでは動くのに常駐だと動かない」の 9 割はこれ。

**3. 実 `claude` を起動するテストは書かない**

1 回のレビュー実行が実費（大きい repo で $0.59 の実績）。`internal/runner` のテストは **shell script の fake claude を PATH に置いて実プロセスを起動する**方式を採用している。exit code / timeout / プロセスグループ kill / 同時実行数はこれで実挙動まで検証できる。新しくプロセス起動系のテストを書くときはこの方式に倣う。

**4. `poll --dry-run` を実装確認の第一手にする**

`reviewd poll --dry-run` は source → store → rule までを実 `gh` で通し、**claude を起動せずに**「何が拾われ、拾われないものはなぜか」を理由付きで出す。ルール・マッチング・イベント取得まわりの変更は、まずこれで確認するのが最も安上がり。

**5. 冪等性は「起動時点」で記録する**

`processed` は claude の成否に関わらず起動した時点で記録する。失敗のたびに無限リトライして API とトークンを溶かす事故を防ぐための設計判断。**再実行は `reviewd run` で手動**。この前提を崩す変更（成功時のみ記録する等）は設計変更なので OpenSpec change を作る。

**6. 実機の状態はコードと独立に消える**

`~/.reviewd/`（mirror / worktrees / runs / state.db）はユーザーが掃除することがある。task ファイルに「実機検証済み」と書いてあっても、`~/.reviewd/` が存在しないなら成果物は残っていない。再現するなら `reviewd init` からやり直す。

## 注意事項

**ファイル操作の禁止事項** (§0 の禁止事項を含む単一の出典):

- 既存 `task.*.md` を **無断で上書きしない**。中身があるなら必ず AskUserQuestion を経る
- 新規作成時に **`task.*.md` 以外の名前を使わない**（gitignore 漏れ事故防止）
- **新規作成は cwd 直下のみ**。`pwd` で確認してから Write する。他の場所に作りたい場合は AskUserQuestion を挟む
- skill 側で `task.*.md` を **コミット / ステージング / 削除しない**。`git add` も含めユーザー操作に委ねる
- **タスク着手時にブランチを切らない / 切り替えない**。`git checkout -b` / `git switch -c` / `git switch` 等のブランチ操作は一切行わず、**現在のブランチのまま作業を始める**。ブランチをどうするかはユーザーが後でよしなに指示するので、skill 側では何も気にしない
- **冒頭 2 行（指示文）を消さない / 書き換えない**。ユーザーの運用ルール

**書き方の原則**:

- **作成した成果物 URL は即時に冒頭 `## 関連リンク` へ**。PR / issue / OpenSpec change を作ったら、作成成功の瞬間にページ最上部へ追記する。後回し・バッチ追記は中断時に失われるので不可
- **チェックリストの即時更新を守る**。バッチ更新は中断耐性を下げる。1 項目完了 → ファイル Edit → 次
- **メモは「意思決定の理由を残しつつ、不要分は掃除」**。採用 / 却下の根拠（### 意思決定の理由）は消さないが、誤りと確定した分析・スコープ外になった対応項目は削除してコンテキストを軽く保つ（ユーザー明示の好み）
- **TodoWrite とタスクファイルは併走**。TodoWrite はセッション内の作業順序管理、`task.*.md` は永続ナレッジ。両方に同じ項目が出るのが正常
- **新規作成モードで雛形を保存する前に必ず AskUserQuestion** を経る。チェックリストの粒度はユーザーの想定に合わせる
- **タスクが大きすぎる場合は分割案を提示**。skill 側で勝手に分割しない
- **`.gitignore` 漏れ確認**（`git check-ignore <ファイル名>`）。グローバル無視にも含まれていない異常系では「コミット前に整理した方が良いか」をユーザーに報告

**外部への副作用を伴う操作は勝手に実行しない**:

reviewd は本質的に「外部コマンドを起動する常駐プロセス」なので、確認なしに実行すると実費・永続的な状態変化が発生する操作がある。以下は **ユーザーの明示指示があるまで実行しない**:

- `reviewd run` / `reviewd poll`（`--dry-run` なし）— 実 claude が起動して課金される
- `reviewd daemon install` / `launchctl bootstrap` — 常駐が始まり、以後自動で課金され続ける
- `reviewd seed` — 既存の未処理イベントを「処理済み」として潰す（取り消せない）
- `git push` / `gh pr create`

## よくある失敗

- **チェックリストを全部済ませてから一気にメモを書く**: 途中の試行錯誤や却下案が抜け落ちる。1 項目ごとに少しずつ書く方が結果的に楽。
- **「原因」を症状で書いてしまう**: 「commit にファイルが入らない」は症状。「gitignore パターンが先頭 `/` 無しで全階層に効いていた」が原因。両者を区別する。
- **修正セクションにファイル名を書かない**: 後で PR description を書くときに grep し直す羽目になる。実装した瞬間に書く。
- **「検証」が空のまま完了報告**: テストを書いていない / 手動確認していないのと同義。何らかの確認手段を必ず書く（無理ならその旨を「未検証」と明記）。
- **外部コマンドの出力形状を憶測で書く**: `gh` の JSON キー名や `claude` の stream-json の形は実際に叩いて確認する。憶測で書いた形状に合わせてパーサを書くと、実機で初めて壊れる。
- **`make test` が通ったことを「動く」と読み替える**: reviewd のテストは大半が fake（fake gh / fake claude / fake runner）。実 `gh` と実 `claude` を通す確認は別途必要で、それは `poll --dry-run` → `run` の順に上げていく。
- **意思決定の理由まで消してしまう**: 不要メモの削除は推奨だが、採用 / 却下の根拠を消すと「なぜこの方向にしたか」が辿れなくなる。掃除するのは誤り確定の分析・スコープ外項目のみ。
- **タスクファイルを勝手に削除 / コミット**: ユーザーの運用領域を侵害。完了後はファイルを残してユーザーに渡す。
- **着手時に気を利かせてブランチを切ってしまう**: ブランチ運用はユーザーの領域。main 上だったとしても skill 側でブランチを作らず、現在のブランチでそのまま作業する。
- **新規作成モードで確認なしに雛形を書き殴る**: チェックリストの粒度がユーザーの想定とズレる。1 度確認を入れる。
- **issue URL / change パスを冒頭に書き忘れる**: 後でコンテキストを辿れなくなる。最初に必ず貼る。
- **config のキー名を変えて雛形テンプレートを直し忘れる**: `internal/cli/templates/*.yaml` が旧キーのままだと `reviewd init` の生成物が `yaml.Strict()` で弾かれる。§6 の 4 箇所 grep を必ず回す。

## 付録: 具体例

タスクファイルが実際にどう書かれ、どう育つかの完全な実例は **同ディレクトリの [`examples.md`](examples.md)** にまとめてある。

- **例 1**: 不具合修正タスクの 3 段階（新規作成直後 → 進行中 → 完了直前）。題材は `.gitignore` の `reviewd` が `cmd/reviewd/` ごと除外していた実際の事故。チェックと `## メモ` 4 見出しが 1 項目ずつ育つリズムが分かる。
- **例 2**: 機能開発 / 大きめタスクで、`### 原因/修正/検証/意思決定` の最小セットに `### 仕様` / `### 実測` / `### 設計判断ログ` / `### 残課題` 等のドメイン見出しを足す書き方。

雛形（§2-c）は最小の骨組み、`examples.md` は「埋まった状態のゴールイメージ」という関係。迷ったら `examples.md` の粒度に寄せる。
